## Recommended design direction

The shape you described fits a two-stage loan lifecycle rather than a one-screen workflow:

1. A customer submits a loan application in an “Applications” area.
2. An admin reviews and approves or rejects that application.
3. A privileged user with issuance rights creates the actual loan record in the Loans area.

That is a cleaner separation than trying to issue a loan straight from the customer form, because it makes the business approval step explicit and prevents the “duplicate issue” problem from being exposed at the wrong layer.

The dashboard shell already has those view-navigation hooks defined in DashboardController.java, but the methods for `showReportsView()` and `showSettingsView()` are still empty, so those are your next UI integration points.

---

## Suggested domain and workflow

### 1. Add a loan application model
Create a new entity like `LoanApplication`:

- `id`
- `customer`
- `principal`
- `interestRate`
- `maturityDate`
- `tenor`
- `collateral`
- `fees`
- `requestedAt`
- `status` values such as:
  - `PENDING_ADMIN_REVIEW`
  - `APPROVED`
  - `REJECTED`
  - `WITHDRAWN`
- `reviewedBy`
- `reviewedAt`
- `adminNote`

The `Loan` entity should remain the actual issued credit instrument.

This lets “applications” and “issued loans” stay distinct:
- Application = request made by a customer
- Loan = approved and issued account movement

---

### 2. Customer-facing application flow
In the Applications view, the customer flow should look like this:

- A customer enters the application form.
- The application stores a row in the new application table.
- The staff/admin sees the pending applications.
- Admin decides:
  - `APPROVE` → the application can be used to derive an issued `Loan`
  - `REJECT` → the application is declined and should not become a loan

That is the right place for the “approved loan application -> issued loan” handoff.

---

### 3. Issuance workflow in the Loans view
Once an application is approved, the privileged user opens the Loans view and selects or creates a loan from that approved request.

A good rule for the UI:
- “Save” must be disabled when a selection is present and the user is trying to create a new record from the table
- Updating an existing loan must be a real update, not “save as new”
- “Issue” should locate the approved application, copy its fields to a `Loan`, and persist the real loan record.

That is where your duplicate prevention rule belongs.

## Reports view design

The existing reporting service already shows the right starting point in ReportService.java:

- daily cash totals
- portfolio summary
- aging logic
- collection buckets

I would expand the Reports UI into three grouped panels:

### Daily summary report
This panel should answer:
- total loans issued today
- total repayments today
- total collection value today
- number of active/pending/defaulted loans
- total outstanding balance
- active field officer performance summary

### Aging analysis report
This should be a table or chart with buckets such as:
- 0–30 days
- 31–60 days
- 61–90 days
- 90+ days

It can draw from the `getAgingAnalysis()` logic already present in the report service. You can expose:
- customers in each bucket
- amount outstanding per bucket
- oldest overdue loan date

### Portfolio/reporting dashboard
This should include:
- loan status counts
- total principal issued
- total principal outstanding
- loan approvals/rejections count
- daily collection trend
- field officer productivity summary

A clean reports tab can be built with:
- top summary cards
- table below it
- charts (optional) once the report models are stable

## Email delivery design

Because the owner wants reports emailed, I would create a small reporting/email layer:

### New service objects
Add a service or orchestration layer like:

- `EmailService`
  - sends SMTP text/HTML email
  - uses Spring Mail or a JavaMailSender adapter
- `ReportEmailJobService`
  - composes daily or weekly report payloads
  - selects recipients from admin settings
- `ReportScheduleSettings`
  - stores frequency and time windows

### Report types
Define two concrete email bundles:

1. Daily statistics email
   - summary totals for the day
   - customer/payment collection totals
   - active loan count
   - loan status counts
   - administrators should receive it daily

2. Aging analysis email
   - outstanding amount by aging bucket
   - most overdue customer accounts
   - account officers assigned to overdue loans
   - should be sent weekly or a configured interval

## Scheduling and settings

The settings view should hold a configuration table or entity such as:

- `AdminEmailSettings`
  - admin email recipients
  - default timezone
  - send daily statistics report: `true/false`
  - aging email cadence: `daily`, `weekly`, `every-3-days`, `fortnightly`, etc.
  - delivery time: e.g. `07:00`

The setup is flexible enough to support:
- once a week
- every three days
- monthly
- configurable custom schedule

I’d recommend storing these settings in the database rather than hardcoding them in code.

You can expose them as:
- `reportSchedule.dailySummaryEnabled`
- `reportSchedule.dailySummaryHour`
- `reportSchedule.agingSchedule`
- `reportSchedule.agingHour`
- `reportSchedule.adminRecipients`

I’d do it in this order:

3. Hook approved applications to the Loans issuance workflow
4. Expand the report service with stable daily and weekly aggregations
5. Introduce `EmailService` and SMTP configuration
6. Add settings persistence for email cadence and admin recipients
7. Create the scheduler around the settings

- Operations/reporting belongs in reports
- Email schedule/recipient setup belongs in settings

## Practical recommendation

For the first pass, use a very simple report model instead of trying to make the reports “smart” immediately:

- A daily job generates a summary dataset
- A weekly job generates an aging dataset
- Both are sent as a simple HTML email to configured admin users
- The scheduling is driven from a settings table

That gives you a working reporting spine now and room to make the report content richer later.
